# Project Status — Calm Navigation Companion

Updated 2026-07-30. This is a coursework Design Thinking prototype, not a funded product with paying customers — the scoring and recommendations below are calibrated to that reality, not to a venture-scale launch.

## What this actually is

A static client-side web app: HTML/CSS/vanilla JavaScript loaded via `<script>` tags, no framework, no bundler, no TypeScript. MapLibre GL + OpenFreeMap vector tiles for the map (recolored per theme from the app's own palette — replaced Leaflet + CARTO raster on 2026-07-30), GraphHopper for geocoding/walk-bike routing, Transitous (open MOTIS) for public-transport itineraries, and OpenStreetMap's Overpass API (three-mirror fallback chain) for places — each proxied through its own Cloudflare Pages Function (`functions/api/route.js`, `geocode.js`, `transit.js`, `pois.js`) so keys stay server-side and free community services are capped/whitelisted rather than hit raw. Deployed on Cloudflare Pages (`calm-navigation-companion.pages.dev`); locally run with `wrangler pages dev .` (Functions-aware) or `python3 -m http.server` (static-only, demo mode). Installable as a PWA (manifest + service worker) for a home-screen icon and offline-tolerant app shell.

**As of 2026-07-28, also a real native app** (iOS/Android via Capacitor, see NATIVE_SETUP.md) — the web/PWA deployment above is unchanged and still the primary, fully-verified surface; the native wrapper adds true background GPS/voice/notifications through a custom plugin, **implemented and code-reviewed but not yet compiled or run** (the authoring machine has no Xcode/Android SDK/Java — see NATIVE_SETUP.md's prerequisites). Treat every native-specific claim in this document as "should work, pending a real build," not as verified fact, until MOBILE_TESTING_CHECKLIST.md has actually been run on physical devices.

## Completed features

- Calm-vs-fastest routing via GraphHopper, scored by road classification (residential/path favored over primary/motorway), with a named peak-hour heuristic.
- A safety-aware alternate scoring mode + automatic night/isolation warning, built in direct response to real user feedback.
- Turn-by-turn step list, parsed from GraphHopper's own `path.instructions`.
- **Live GPS navigation**: real `watchPosition` tracking, live position marker with heading rotation, automatic step advancement, distance/ETA readouts, automatic off-route detection and rerouting (3-fix hysteresis so one bad GPS reading doesn't trigger a reroute), dedicated arrival screen.
- Follow-mode / recenter UX: the map auto-follows the user; a manual pan disables auto-follow and shows a recenter button instead of fighting the gesture.
- Optional on-device voice guidance (Web Speech API), muted by default, with no-repeat tracking per instruction.
- Screen wake lock during active navigation, where the browser supports it.
- Travel mode selector (Walk / Bike), sent to GraphHopper as the routing profile.
- Special-event awareness: a named, partial heuristic (King's Day, New Year's Eve) that discloses — rather than silently ignores — a real gap in the calm/safety scoring.
- Developer GPS simulation mode (`?simulate=1` or `config.js` flag), clearly badged on-screen, walking a fake position along the real fetched route at real (or accelerated) walking speed, for testing/demoing without physically walking.
- Auditory regulation (synthesized noise, Web Audio API) and haptic fidgeting (Vibration API + musical pentatonic tones + visual ripple fallback on iOS, which has no Vibration API at all).
- Accessibility settings: reduced motion, high contrast, dark/light theme.
- Installable PWA: `manifest.json`, `sw.js` (same-origin app-shell caching, cross-origin map tiles/routing untouched; skips registration on localhost for dev sanity), home-screen icon, iOS 17+ playback audio session so installed-app audio survives the ringer switch.
- **2026-07-30 pass** (see git log for the full trail): MapLibre GL vector map themed per app palette; search-bar-first planning screen with tap-to-navigate and nearby café/bar name suggestions; one-route default with the alternative behind a disclosure; Transit travel mode (Transitous itineraries incl. ferries, drawn on-map); OSM places layer at density (400/400/150 per area, GL circle rendering, Overpass mirror chain); 15-tine kalimba with two-layer Echo recording pinned to the real recording location; labeled nav controls with an always-visible Stop; assorted device-reported fixes (search re-lock after stopping navigation, stale-fix Echo placement).
- **Location-aware address autocomplete** (2026-07-28): both start/destination fields are accessible comboboxes with live suggestions (streets, addresses, stations, parks, landmarks), ranked by a named-weight model that puts text-match strength ahead of proximity/city (so a strong match elsewhere still beats a weak match nearby, but ties within a tier resolve by distance/city/country). Debounced (300ms), stale-response-safe (sequenced + aborted), full keyboard support, "Use my current location" pinned in the start field only. See the README's "Address autocomplete" section for the full architecture.
- **Native iOS/Android app via Capacitor** (2026-07-28): a custom plugin (`plugins/calm-nav-background/`, Swift + Kotlin) adds background-capable GPS tracking, native TTS voice guidance, an Android persistent notification, and iOS Now Playing/Control Center lock-screen controls — see NATIVE_SETUP.md / IOS_BACKGROUND_NAVIGATION.md / ANDROID_BACKGROUND_NAVIGATION.md. Both native projects (`ios/`, `android/`) generated and confirmed to correctly link the custom plugin (verified via the generated `Package.swift`/Gradle settings). **Not yet compiled, run, or device-tested** — no Xcode/Android SDK in this environment.
- **Calm Echoes** (2026-07-28): the app's signature feature — a premium virtual Kalimba, recorded short melodies + optional messages left at real places, a walk-500m-plus-~3min unlock mechanic, and glowing map-marker discovery, unified into one experience. First-ever database for this project (Cloudflare D1). Full writeup — architecture, schema, API, privacy/security/accessibility analysis, production-readiness score, testing checklist, deployment steps — in **CALM_ECHOES.md**. Backend fully verified end-to-end against a real D1 instance; 99 new unit tests (243 total); the one genuine remaining gap is real/simulated-GPS on-device verification of the walk-to-unlock path, the same category of honestly-disclosed gap as the native app's GPS/audio testing status above.
- 119 automated unit tests (`node --test` + one ESM file for the Cloudflare Function itself) covering the navigation state machine, GraphHopper request/fallback/timeout handling, the geocode+route proxy contract, gesture recognition, voice queueing, autocomplete ranking/geocoding/debounce logic, and the native-app support logic (route-payload validation, reroute backoff, foreground-state reconciliation) — zero new JS dependencies for the app itself (Capacitor and its official plugins are new native-only dependencies, documented in NATIVE_SETUP.md).
- Config/secrets pattern: the GraphHopper key is a Cloudflare Pages secret (`GRAPHHOPPER_API_KEY`), consumed only by `functions/api/*.js`. `config.js` holds no secret and is safe to commit; local Functions-aware dev reads `.dev.vars` (gitignored, see `.dev.vars.example`). The native app calls the same endpoints cross-origin (`config.js`'s `NATIVE_API_BASE_URL`); both Functions now send a permissive CORS header for this reason (see PRIVACY_LOCATION_DISCLOSURE.md for why that's safe — no cookies/auth, no per-user data).

## Incomplete / not built

- **Structured field research** (Stage 4/15 in the Design Thinking pipeline): real interviews with multiple subjects have never been run. One informal feedback message from a friend is the only real-world input so far.
- **Full map rotation** (compass-up, like Google/Apple Maps): vanilla Leaflet doesn't support rotating the whole map view without an additional plugin. Only the user's own position marker rotates to show heading.
- **True background navigation on the web/PWA**: unchanged limitation — a browser tab has no background execution once backgrounded or the phone is locked. **Now addressed separately** by the native iOS/Android app (see NATIVE_SETUP.md) — but that native background capability itself has not been compiled or device-tested yet (see below).
- **Native background navigation, device-verified**: the Swift/Kotlin engine, permission staging, foreground service/lock-screen controls, and reroute-with-backoff are all written and code-reviewed, but have never been compiled (no Xcode/Android SDK available) or run on a simulator/emulator/physical device. MOBILE_TESTING_CHECKLIST.md is the concrete list of what remains to actually verify this claim.
- **App-store distribution**: not submitted anywhere. Needs a paid Apple Developer account ($99/yr) and/or Google Play Console account ($25 one-time), a real privacy policy (PRIVACY_LOCATION_DISCLOSURE.md is the factual basis for one, not a substitute), app icons regenerated from a higher-resolution source (current source is 512×512; Apple recommends 1024×1024 for the App Store marketing icon), and review time.

## Known issues

- GPS-position-to-route distance uses nearest-vertex haversine distance rather than true point-to-segment projection. Accurate to a couple of meters at GraphHopper's walking-route point density — inside the off-route margin — but not mathematically exact.
- The developer GPS simulator uses `setInterval`, which browsers throttle heavily in backgrounded/inactive tabs; it compensates by advancing based on real elapsed time rather than tick count, but a fully backgrounded tab will still visibly "jump" rather than animate smoothly.
- No error boundary / global crash handler; a JS exception in one pillar's code could, in principle, take down the page rather than degrading gracefully. Not explicitly guarded against, though the 2026-07-28 audit (see below) found and fixed the one real instance of this (the sound-canvas crash).
- Pressing "Find calm route" fires 1 route request always, plus a geocode request per field **only if that field's text no longer matches an autocomplete selection** — picking a suggestion and leaving it untouched skips re-geocoding it entirely now. In demo mode (no key configured) these calls fail fast (~10-50ms) rather than hang, so it's a minor efficiency note, not a UX issue.
- No "nearby destinations" / "recent searches" quick-pick in the destination field — a deliberate scope cut (see README), not a gap: adding it would mean deciding on and storing search history, which conflicts with the "no location history persisted" privacy stance taken elsewhere in this feature.

## Technical debt

- No build step means no TypeScript, no linting pipeline, no bundling/minification — acceptable for a project this size, but it also means nothing catches a typo'd variable name except manual testing or the browser's own runtime error. (This is exactly how the sound-canvas bug below shipped silently for a full day.)
- `app.js` is a single ~1000-line file. The navigation *logic* is now cleanly separated (`navlogic.js`), but the navigation *UI wiring* still lives inline with the other two pillars' wiring in the same file.
- No dependency-vulnerability scanning process exists, but there is also exactly one runtime dependency (Leaflet, loaded from a CDN) — the surface area is small by construction, not by process.

## 2026-07-28 production-hardening audit

A full-codebase pass (all 16 source files read, not sampled) found and fixed:
- **Critical**: `drawSoundCanvas()` referenced undefined globals (`audio`, `volSlider` — stale names from before a rename), throwing on its first animation frame every single page load and silently killing the Auditory Regulation page's sound-level visualizer. Never showed up in manual testing because it fails silently (no visible crash, just a permanently blank canvas) unless devtools console is open.
- **High**: one-sided geocode failures (start resolves, destination typo doesn't, or vice versa) were silently swallowed — the app would navigate using a stale/default location with no warning. Now checked and reported independently per field.
- **Medium**: a race condition — toggling "prefer well-lit streets" or switching Walk/Bike while a search was already in flight could fire a second overlapping `fetchCalmRoute()` call. Now guarded with an `isSearching` flag.
- **Medium**: no timeout on GraphHopper requests — a hung request left the UI stuck on "Finding your calm route…" indefinitely. Now bounded (12s default, `AbortController`-based), tested.
- **Security**: the GraphHopper key shipped in client-side `config.js`, readable via devtools by any visitor. Moved behind two Cloudflare Pages Functions (`functions/api/route.js`, `functions/api/geocode.js`); the key is now a Pages secret, never sent to the browser. Verified: `curl` on the deployed `config.js`/`app.js` shows zero occurrences of the key.
- **Accessibility**: the reduced-motion toggle never read the OS-level `prefers-reduced-motion` preference on load, and the two ambient canvas animations (ripple fidget feedback, sound-level bars) ran forever regardless of that setting or tab visibility. Now: OS preference sets the default on load, the sound-canvas animation (true ambient/non-interactive motion) respects it and pauses in background tabs, and the ripple canvas (direct gesture feedback, intentionally exempt from the reduced-motion gate) stops rescheduling itself once idle instead of animating an empty canvas forever.
- Dead code (`calmCard.querySelector(".rc-dist") ? null : null;`, a no-op ternary) removed.
- Map tile-gap bug and route-card/Start-button ordering bug (found and fixed earlier the same day — see git log) — still holding, reverified during this pass.

## 2026-07-28 address autocomplete build

Added live, location-aware autocomplete to both address fields (previously: plain text, resolved only once, on "Find calm route," via a single `limit=1` geocode call with no ranking, no location bias, no reverse geocoding at all). Three real bugs surfaced and fixed during the build, worth recording since none were obvious from reading the code in isolation:
- **Cross-file naming collision**: `geocodingservice.js` declared its own `const REQUEST_TIMEOUT_MS`, already declared by `routing.js`. Classic `<script>` tags on one page share a single top-level lexical scope for `let`/`const`/`class` — this was a silent `SyntaxError` that killed the entire second script with **no console output at all** (uncaught parse errors don't surface as `console.*` messages), leaving every function in that file undefined. Renamed to `GEOCODE_REQUEST_TIMEOUT_MS`; also swept all other new top-level names against every existing script for the same class of collision (none found).
- **Dedup logic bug**: `dedupeHits()`'s duplicate-detection closure checked `s.type` on a stored record that only ever had `{labelKey, bucket, hit}` — `s.type` was always `undefined`, so the type-match guard silently always failed differently than intended. Fixed to `s.hit.type`; also simplified the function from a bucket-prefilter-plus-fallback shape to a plain "same label AND same type AND <40m apart" check after a fabricated same-coordinate/different-name test case exposed the original OR-based fallback as too aggressive.
- **Browser cache during manual testing**: after fixing the above, the running `wrangler pages dev` kept serving a browser-cached pre-fix copy of both the script and `index.html` despite a normal reload — only a cache-busting query string / hard reload actually picked up the fix. Worth remembering for any future manual QA pass on this project: a normal reload is not guaranteed to bypass cache here.

Also fixed in passing: the reduced-motion CSS rule `input:focus-visible { outline: ... }` was being silently overridden by a later, equal-specificity `.route-input-row input { outline: none; }` — meaning the start/destination fields had **no visible keyboard-focus indicator at all** before this change. Fixed with a `.route-input-row:focus-within` ring on the whole row (a shape change, not colour alone) rather than removing the inner `outline: none`.

## 2026-07-28 native iOS/Android build

Added a Capacitor-wrapped native app around the existing, unmodified web app, plus a custom `calm-nav-background` plugin (Swift + Kotlin) for true background GPS/voice/notifications. Several real bugs surfaced during the build — worth recording since none were obvious from reading either language's code in isolation:

- **Load-order bug**: the Capacitor bridge script (`capacitor.js`, which defines `window.Capacitor`) was initially injected at the *end* of `index.html`'s script list — after `app.js`, which reads `Capacitor.isNativePlatform()` at load time via `shared/navigationBridge.js`. This would have made every native build silently behave as if it were the web build. Fixed by moving the injection point to the very first script tag.
- **The web deployment never loaded the new shared/web/native modules at all**: they were only being injected into the Capacitor-only `www/index.html` copy, not the source `index.html` that Cloudflare Pages actually deploys — meaning the live web app would have thrown `ReferenceError: NavBridge is not defined` on its very first new line of code. Fixed by adding the script tags directly to the one source `index.html` (harmless on web: `window.Capacitor` is simply undefined there, so `NavBridge.isNative` evaluates to `false` and every existing code path behaves exactly as before).
- **The custom plugin wasn't actually linked into the generated Xcode project**: Capacitor 8's iOS template uses Swift Package Manager exclusively (no `Podfile` is generated at all), and SPM requires each plugin to ship its own `Package.swift` — a podspec alone (what was initially written) is invisible to it. `npx cap add ios` silently warned and skipped the plugin. Fixed by adding a `Package.swift` to the plugin and removing the now-redundant/riskier Objective-C `CAP_PLUGIN` macro registration (the current official plugin template no longer uses it alongside `CAPBridgedPlugin`).
- **Missing CORS headers**: the native app's WebView origin differs from the Cloudflare Pages origin, making every `/api/geocode` and `/api/route` call cross-origin from the native app's point of view. Neither Function set an `Access-Control-Allow-Origin` header, which would have silently blocked the native app from ever reading a response. Fixed by adding a permissive header to both (safe here: no cookies/auth, no per-user data in these responses).
- **A Kotlin file had literal Swift syntax** (`_ = expr` as a discard statement) left over from writing the two ports back-to-back — caught by manual re-review, not a compiler (none was available). A reminder that hand-written, unverified native code in two languages needs its own explicit review pass, not just "looks right."

None of the above would have been caught without deliberately tracing the actual script-load order and the actual generated native project files rather than trusting the source code alone — worth remembering for the next native-adjacent change to this project.
